# Case Study: Building LogiTrack on Microsoft Fabric

## 1. The problem

A logistics company ships orders across four US regions. Order data, shipment data and weekly regional sales files arrive in inconsistent shapes, and policy knowledge lives in documents. The goal: one trusted, secured platform that analysts can report from and that a chatbot can safely answer questions against.

The data is synthetic, generated by `data/generate_data.py` with a fixed random seed. Defects were injected deliberately so the cleaning work is real: duplicate rows, missing customer names, region values in mixed casing and with stray spaces, four different date formats, and zero or negative quantities.

## 2. Ingestion (Bronze)

Raw CSVs are read from `Files/raw/...` and written as Delta tables in a `bronze` schema. Every row gets `_ingested_at`, `_source_file` and `_source_system` so any value can be traced back to its file.

Landed: 1,028 orders, 944 shipments, 48 regional-sales rows.

The first version used `inferSchema=true` and an overwrite on each run. Section 5 covers the second version.

## 3. Cleaning (Silver)

| Rule | Implementation | Why |
|---|---|---|
| Remove exact duplicates | `dropDuplicates` on business-key columns | Re-exports created repeated rows |
| Standardise region | `initcap(trim(region))` | `east`, `EAST`, ` East` all become `East`; verified as exactly four distinct values with lengths 4 or 5 |
| Parse dates | Try four formats in order and `coalesce` | Sources mixed `yyyy-MM-dd`, `MM/dd/yyyy`, `dd-MM-yyyy`, `yyyy/MM/dd` |
| Quarantine, do not delete | Rows with quantity <= 0, unparseable dates or missing customer names go to `silver.orders_quarantine` with `_quarantine_reason` | Preserves an audit trail |

Results:

| Table | Bronze rows | Exact duplicates removed | Quarantined | Silver clean rows |
|---|---|---|---|---|
| orders | 1,028 | 28 | 61 | 939 |
| shipments | 944 | 19 | 0 | 925 |

**Known ambiguity:** `dd-MM-yyyy` and `MM-dd-yyyy` conflict for any date where both day and month are 12 or lower. The parser takes the first matching format. This is documented in the code rather than hidden. A production version would fix the format per source system.

**A verification worth mentioning:** the region column looked as though it had leading spaces in the notebook's table output. Instead of assuming, a query checked `length(region)` and bracketed the value (`[East]`). The values were clean; the spacing was display padding.

## 4. Modelling and reporting (Gold)

`dim_customer` is a Type 2 dimension with a surrogate key, `effective_date`, `end_date` and `is_current`. `fact_orders` and `fact_shipments` join to it. `agg_regional_performance` pre-aggregates revenue, order count, average order value and average delivery days for delivered shipments.

Row counts carried through exactly: 939 orders in Silver and Gold, 925 shipments in Silver and Gold, so no rows were lost in the joins.

| Region | Orders | Revenue | Avg delivery days |
|---|---|---|---|
| North | 260 | $109,100.15 | 5.33 |
| South | 258 | $97,979.49 | 5.54 |
| East | 216 | $83,278.93 | 5.19 |
| West | 205 | $69,118.27 | 5.36 |

Top product by revenue is the Standing Desk ($138,852.00); the lowest is the Wireless Mouse ($6,936.53).

The Power BI report reads these tables through a Direct Lake semantic model.

**Honest status of SCD2:** the initial load was run and produced 287 current customer rows. The branch that expires a changed record and inserts a new version is written but has never been run against a real change, and the synthetic data does not change a customer's region over time. Testing that path is on the roadmap.

**Relationship caveat:** `fact_shipments` joins to the dimension on `customer_id`, not the surrogate key. That is fine while each customer has one row, and should change once history accumulates.

## 5. Cost and performance

**What was measured**

- Fabric Capacity Metrics, 14-day view, capacity `F2`: notebook runs accounted for 14,260.68 of 16,867.21 CU-seconds, about 85% of all compute in the workspace. Notebooks are where optimisation effort belongs.
- Utilisation was low (about 4.4% average over the period) with no throttled or rejected operations, though there was a brief spike from the first heavy runs.

**What was changed** (`notebooks/01b_bronze_ingestion_optimized.py`)

1. **Explicit schema instead of `inferSchema`.** Schema inference makes Spark read the file an extra time to guess column types. Defining the schema removes that pass.
2. **Incremental loading.** A watermark table per source records processed file paths. On the next run, files already recorded are skipped.

**What the run showed**

| Run | Time |
|---|---|
| First run, three tables loaded in full | 25.7 s |
| Second run, orders only, no new files ("[SKIP]") | 2.8 s |

**Caveat, stated plainly:** these two timings are not a like-for-like comparison. The first run loaded three tables and the second only checked one. The result demonstrates that the skip logic works and costs very little when nothing has changed. It does not prove a specific percentage saving. Also, the runtime of the original notebook was never captured. To make this rigorous: run the original and optimised notebooks against the same three tables, then compare the CU-seconds for each run in the Capacity Metrics **Item History** view.

## 6. GenAI RAG assistant

**Design** (`notebooks/04_genai_rag_chatbot.py`)

1. Split the policy document on blank lines and keep paragraphs longer than 80 characters: 17 chunks.
2. Embed each chunk (1,536 dimensions) and store text and vectors in `rag.policy_chunks`.
3. For a question: embed it, rank chunks by cosine similarity, take the top 3.
4. Pull the regional figures from `gold.agg_regional_performance` and format them as text.
5. Send the chunks and figures as instructions to the model with the rule: answer only from this context, say so if the answer is not there, and cite which context was used.

**Why this is "governed" AI:** numeric answers come from the curated Gold layer, not from raw or ungoverned tables, and the model is told to refuse rather than guess.

**Results on three test questions**

| Question | Behaviour |
|---|---|
| Average delivery *delay* for East, plus refund policy | Answered the policy correctly (50% shipping refund after 5 business days late; automatic; credited within 3 business days). Declined the delay figure because the data holds delivery days, not delay against the promise. |
| Options for a lost order | Full refund or free replacement, from the policy text. |
| Highest-revenue region and office-furniture return window | North, $109,100.15 (from Gold); 14 days plus a 15% restocking fee if assembled (from policy). |

These are three hand-picked questions, so this shows the pipeline works, not that it is robust. A proper evaluation set with expected answers is a next step.

**Limitations:** cosine similarity is computed in pandas after loading all chunks, which suits tens of chunks and not millions. Chunking by blank lines is simple. Only one document is indexed.

## 7. Governance

- **Row-level security:** four roles, each filtering `region` on the three fact and aggregate tables. The filter logic was validated by running `CALCULATETABLE(... [region] = "East")` against `fact_orders`, which returned 216 orders and matched the aggregate.
- **Not verified end to end:** the roles have no members assigned, and Fabric's "Test as role" returned "does not work with Single Sign-On" on this Direct Lake model. Creating a fixed-identity cloud connection and mapping the model to it did not clear the error. The result is a documented platform limitation rather than a claim that RLS was tested with a real second user.
- **Lineage:** Fabric's item lineage shows Lakehouse → semantic model → report automatically. It is item-level, not column-level, and Microsoft Purview is not integrated.
- **AI data-residency trade-off:** the built-in AI functions need the tenant setting "Data sent to Azure OpenAI can be processed outside your capacity's geographic region" enabled for a capacity in India. That is acceptable for synthetic data and would need review for regulated data.

## 8. Delivery (CI/CD)

A deployment pipeline promoted the Lakehouse, notebook, semantic model and report from Development to Test to Production. Both promotions reported "Successful deployment", and the Test and Production workspaces were created by the pipeline.

Limits to be aware of: deployment copies item definitions, not Lakehouse data; and Git integration is documented ([git-integration.md](git-integration.md)) but not yet connected.

## 9. Platform constraints met, and how they were handled

Most of the elapsed time went here, and it is useful interview material.

| Constraint | Symptom | Resolution |
|---|---|---|
| Fabric free trial not available | "A Fabric trial isn't available for your account" | Used an F2 capacity provisioned through Azure instead |
| Personal Microsoft account | "You cannot create a Microsoft capacity using a personal account" | Created an organisational user in the tenant's directory and signed in as that user |
| Semantic model table list empty | No tables shown in the New semantic model dialog | Refreshed the table list |
| Report opened in Viewing mode | Manage roles greyed out | Switched to Editing mode |
| "Test as role" blocked | "does not work with Single Sign-On" | Validated the filter with a DAX query; documented as a limitation |
| Azure OpenAI region rejected | `RequestDisallowedByAzure` (Azure for Students allowed-regions policy) | Switched to Fabric's built-in AI access instead of provisioning a separate resource |
| AI call blocked | `DisallowedForCrossGeo` | Enabled the cross-region processing tenant setting |
| AI library signature | `responses()` missing `instructions` | Passed the system instructions as a separate argument |
| Capacity Metrics app install | Capacity ID entered in the wrong field | Corrected the parameters (UTC offset 5.5 for India) |
